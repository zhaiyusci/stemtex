# Distribution Options

This project can be distributed in three practical ways.  They differ mainly in
who owns the TeX tree and who can update packages.

## Option A: StemTeX Embedded Runtime

This is the current small-tree model.  StemTeX is a trimmed Windows XeLaTeX
runtime with the patched daemon engine, a fixed STEM-oriented package set, XITS
Math, and Windows system text/CJK fonts.

```text
stemtex\
  bin\windows\
    xetexdaemon.exe
    xetexdaemon.dll
    xelatexdaemon.bat
    xdvipdfmx.exe
    required DLLs
  texmf-dist\
  texmf-var\
  run-xelatexdaemon.bat
  refresh-font-cache.ps1
```

Build script:

```powershell
.\scripts\build-windows-native.ps1 -Target All -Arch x64

.\scripts\build-stemtex-runtime.ps1 `
  -TeXLiveRoot C:\texlive\2026 `
  -Destination .\stemtex `
  -Clean
```

Measured local size:

```text
stemtex      57.92 MB   713 files
```

Strengths:

- Small enough to embed in an application.
- The runtime is controlled and reproducible.
- No user TeX Live installation is required.
- Fast and predictable after fontconfig cache warmup.
- Uses only daemon names in the shipped runtime, not `xetex.exe`,
  `xelatex.exe`, or `xetex.dll`.

Costs:

- No `tlmgr`.
- Users cannot freely install arbitrary packages inside this runtime.
- If the fixed preamble changes enough to need new packages/fonts, the vendor
  rebuilds and ships a new runtime.

Use this when the product has a known preamble and snippets are ordinary CJK,
English, math, chemistry, physics, and color content.  The default preamble
currently loads `mathtools`, `mhchem`, `physics`, `xcolor`, and `cancel` on top
of `unicode-math` and `xeCJK`.

The embedded tree also includes `siunitx` for alternate preamble variants, but
it is not loaded by the default low-latency preamble because it conflicts with
`physics` over `\qty`.

## Option B: StemTeX Portable TeX Live With tlmgr

This is a maintainable mini distribution, not a hand-trimmed runtime.  It keeps
TeX Live's package database and `tlmgr`, while the patched XeTeX engine lives in
an overlay directory so `tlmgr update --all` cannot overwrite it.

```text
dist\stemtex-tlmgr\
  texlive\
    bin\windows\
      tlmgr.bat
      kpsewhich.exe
      xdvipdfmx.exe
      stock TeX Live binaries
    texmf-dist\
    texmf-var\
    tlpkg\
      texlive.tlpdb
  patched-bin\windows\
    xetexdaemon.exe
    xetexdaemon.dll
    xelatexdaemon.bat
  renderer-tlmgr.bat
  run-xetexdaemon.bat
  run-xelatexdaemon.bat
  refresh-renderer.ps1
```

Build script:

```powershell
.\scripts\build-windows-native.ps1 -Target All -Arch x64

.\scripts\build-tlmgr-texlive-xetexdaemon.ps1 `
  -InstallTl C:\path\to\install-tl-windows.bat `
  -SourceRoot .. `
  -Destination .\dist\stemtex-tlmgr `
  -Clean
```

Users can maintain packages with:

```powershell
.\renderer-tlmgr.bat install siunitx
.\renderer-tlmgr.bat update --all
.\refresh-renderer.ps1 -Clean
```

Measured local size:

```text
stemtex-tlmgr         531.0 MB   22279 files
```

Strengths:

- Users can install/update TeX Live packages with `tlmgr`.
- The application still uses the patched service engine.
- The patched engine is outside `texlive\bin\windows`, so normal TeX Live
  updates do not replace it.

Costs:

- Much larger than the hand-trimmed runtime.
- `tlmgr` works at TeX Live package granularity, not at individual-file
  granularity.  Installing `xeCJK`, `fontspec`, `unicode-math`, and friends
  pulls many dependencies.
- The daemon format must be built with `xetexdaemon`, not with stock XeTeX.
  A format generated by a different executable version can fail to load.

Use this for an "advanced" distribution where package self-maintenance matters
more than size.

## Option C: Overlay Into The User's TeX Live

This option assumes the user already has a full TeX Live installation.  The
application ships only the patched engine overlay and renderer code.

```text
MyApp\
  renderer\
    server.js
    worker-webapp.tex
  xetexdaemon\
    xetexdaemon.exe
    xetexdaemon.dll
    xelatexdaemon.fmt
    setup-user-texlive.ps1
    run-xelatexdaemon.bat
```

At setup time:

```text
1. Find the user's TeX Live bin directory.
2. Verify kpsewhich, xelatex.ini, xdvipdfmx, and required packages.
3. Put xetexdaemon before the user's TeX Live bin directory in PATH.
4. Build a daemon-specific format with xetexdaemon.
5. Run a warmup document to check fonts and cache behavior.
6. Save the discovered paths in renderer config.
```

Example command shape:

```powershell
.\xetexdaemon\xetexdaemon.exe -ini -etex -jobname=xelatexdaemon xelatex.ini

.\xetexdaemon\xetexdaemon.exe `
  -fmt=.\xetexdaemon\xelatexdaemon `
  --no-font-cache-refresh `
  -no-pdf `
  ...
```

Strengths:

- Smallest application download.
- Users keep using their own `tlmgr` and full TeX Live.
- No need to distribute hundreds of megabytes of TeX packages.

Costs:

- Requires an existing user TeX Live installation.
- The app must discover and validate the user's TeX Live.
- Version compatibility matters.  The safest setup builds a daemon-specific
  format with the daemon executable instead of reusing the user's `xelatex.fmt`.
- Font cache policy is partly delegated to the user's TeX Live environment.

Use this for expert users or environments where TeX Live is already installed.

## Recommended Product Shape

Ship more than one channel:

```text
Default embedded component:
  Option A, StemTeX embedded runtime.
  Small, controlled, works out of the box.

Advanced package-maintained component:
  Option B, portable TeX Live with tlmgr.
  Larger, but user-maintainable.

Existing-TeX integration:
  Option C, xetexdaemon overlay.
  Smallest download, relies on user's TeX Live.
```

The renderer protocol can stay the same across all three:

```text
render(snippet, widthPt) -> PDF
refresh()
shutdown()
```

Only the runtime discovery and command launcher differ.

## Font Cache And Glyphs

`--no-font-cache-refresh` mostly affects cold startup and first font discovery.
It is not a per-snippet typesetting accelerator after the live worker is hot.

New glyphs in an already selected font are normally handled by `xdvipdfmx` when
it subsets the selected page.  The important boundary is new font instances:
CJK fallback fonts, bold/italic variants, new math alphabets, or different
OpenType fonts.  Those should be covered by warmup or by a manual refresh step.

For Option A and Option B, treat fontconfig cache as runtime/installation state.
For Option C, either use the user's TeX Live font cache or run a first-time
warmup with the daemon setup script.

## Current Preference

For an embeddable software component, Option A remains the default.  It is the
smallest controlled package and matches the fixed-preamble snippet-rendering
product goal.

Option B is viable but large.  It is best treated as an advanced distribution
for users who explicitly want `tlmgr`.

Option C is attractive for expert users because it keeps the app small while
letting the user's own TeX Live provide package management.
