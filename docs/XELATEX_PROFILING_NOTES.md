# XeLaTeX Profiling Notes

This note records the current profiling results for the small XeLaTeX runtime
tree and the fixed-preamble experiments.

## Runtime Under Test

The timings below were taken with the small runtime tree:

```text
mini-rebuild-test
```

The engine is the locally built native Windows XeTeX:

```text
mini-rebuild-test\bin\windows\xetex.dll
mini-rebuild-test\bin\windows\xelatex.exe
```

The wrapper runs XeLaTeX with:

```text
--no-font-cache-refresh
```

Fontconfig caches are treated as runtime data and are pre-generated during the
small-tree build using `test\test_5.tex`.

## Common Preamble

The test files share this preamble:

```tex
\documentclass{article}
\usepackage{unicode-math}
\usepackage{xeCJK}
\usepackage[version=4]{mhchem}
\usepackage{physics}
\usepackage{xcolor}
```

It lives in:

```text
test\preamble.tex
```

`test_1.tex` through `test_5.tex` include it with:

```tex
\input{preamble.tex}
```

## Baseline Split

With warmed fontconfig caches, complete XeLaTeX runs were around 1.3-1.6 s.
The `xdvipdfmx` part was much smaller, around 70-120 ms.

Representative split:

| --- | ---: | ---: | ---: |
| `test_1.tex` | 1462.8 ms | 1272.7 ms | 97.2 ms |
| `test_2.tex` | 1318.8 ms | 1370.3 ms | 100.1 ms |
| `test_3.tex` | 1502.4 ms | 1456.6 ms | 89.1 ms |
| `test_4.tex` | 1369.0 ms | 1268.8 ms | 68.7 ms |
| `test_5.tex` | 1579.9 ms | 1437.0 ms | 116.9 ms |

The main cost is therefore not the PDF driver.  Most time is in XeLaTeX startup,
package loading, font initialization, and document processing.

## Full Preamble Format Attempt

An experiment was made in:

```text
test\format-profile
```

The attempted format source was:

```tex
\input{../preamble.tex}
\dump
```

This failed because XeTeX cannot dump a format after native OpenType fonts or
font mappings have been opened:

```text
! Can't \dump a format with native fonts or font-mappings.
```

This is triggered by the font-related part of the fixed preamble, especially
`fontspec`, `unicode-math`, and `xeCJK`.

Log:

```text
test\format-profile\xelatex-preamble.log
```

Conclusion: the complete fixed preamble cannot be directly preloaded into a
normal XeTeX format without deeper XeTeX changes.

## Takeaways

- `xdvipdfmx` is necessary for the XeLaTeX/XDV-to-PDF path and is not the main
  bottleneck in the current tests.
- Treating fontconfig cache as runtime data is worthwhile and already handled
  by the small-tree build script.
- A full fixed-preamble format is blocked by XeTeX's native-font dump
  restriction.
- `xelatex-packages.fmt` is a viable optional optimization.  It saves roughly
  190-410 ms in the current tests.
- The largest remaining fixed cost is still the font stack:
  `unicode-math`, `fontspec`, and `xeCJK`.

## Delivery Option

If this optimization is used, the small runtime can ship:

```text
texmf-var\web2c\xetex\xelatex-packages.fmt
```

The launcher or wrapper can default to:

```text
xetex.exe -fmt=xelatex-packages -progname=xelatex ...
```

This keeps the user-facing command as XeLaTeX while using the partial preloaded
format internally.

## No-Hyphenation Penalty Format

Because the target workload does not need word hyphenation, a partial format was
tested with paragraph parameters that discourage hyphenation and make TeX accept
the first non-hyphenated pass:

```text
partial-fmt-packages-nohyphen.tex
xelatex-packages-nohyphen.fmt
```

Format source:

```tex
\RequirePackage[version=4]{mhchem}
\RequirePackage{physics}
\RequirePackage{xcolor}
\pretolerance=10000
\hyphenpenalty=10000
\exhyphenpenalty=10000
\dump
```

This does not remove hyphenation patterns from the base LaTeX format; it only
changes paragraph-breaking parameters.

`test_4.pdf` was rendered to PNG and visually checked.  CJK rendering was normal.

Timing comparison against the current-root `xelatex-packages.fmt`, 5 runs each:

| Test | Packages fmt | No-hyphen fmt | Saved |
| --- | ---: | ---: | ---: |
| `test_1.tex` | 1182.1 ms | 1140.1 ms | 42.0 ms / 3.6% |
| `test_2.tex` | 1162.8 ms | 1111.2 ms | 51.6 ms / 4.4% |
| `test_3.tex` | 1153.7 ms | 1139.3 ms | 14.4 ms / 1.2% |
| `test_4.tex` | 1241.4 ms | 1105.9 ms | 135.5 ms / 10.9% |
| `test_5.tex` | 1164.1 ms | 1214.9 ms | -50.8 ms / -4.4% |

Raw data:

```text

```

Takeaway: this is more promising than `\nofiles`.  It improved 4 of 5 tests,
with the largest gain on the long CJK document.  It should still be treated as
an optional mode because math-heavy `test_5.tex` was slower.

## Hot Worker Prototype

For interactive snippets, a long-lived XeLaTeX worker was tested to avoid the
per-request cold start.  The worker loads the fixed preamble once, then waits
for snippet requests:

```text
worker-file-request-prototype.tex
```

The request body is passed indirectly through UTF-8 files, while stdin carries
only ASCII file names.  This is important on Windows: sending UTF-8 Chinese text
directly over the interactive stdin pipe produced replacement question marks.
One bad run also wrote request files through a garbled path and produced the
same failure; those outputs are ignored.

The corrected request files are:

```text
profile-worker-file-prototype-fixed\requests\req1.tex
profile-worker-file-prototype-fixed\requests\req2.tex
profile-worker-file-prototype-fixed\requests\req3.tex
profile-worker-file-prototype-fixed\requests\req4.tex
profile-worker-file-prototype-fixed\requests\req5.tex
```

Timing result:

| Metric | Result |
| --- | ---: |
| Startup to `WORKER_READY` | 985.1 ms |
| Total process time, 5 requests | 1150.5 ms |
| Average hot request time | 16.4 ms |

Per-request timing:

| Request | Time |
| --- | ---: |
| 1 | 13.5 ms |
| 2 | 16.6 ms |
| 3 | 47.5 ms |
| 4 | 2.6 ms |
| 5 | 2.0 ms |

Raw data:

```text
profile-worker-file-prototype-fixed\summary.json
```

The resulting PDF was rendered to PNG and visually checked.  Chinese text,
`unicode-math`, `mhchem`, and `xcolor` output were normal:

```text
profile-worker-file-prototype-fixed\render
```

This is the strongest speed result so far: once the preamble and font stack are
hot inside a live process, small snippets can be typeset in tens of
milliseconds.

There is a major remaining output limitation.  A live-file check showed that
XeTeX does not produce a usable output file while the worker is still running:

| Output mode | During worker | After worker exit |
| --- | --- | --- |
| PDF | no file | complete PDF |
| XDV via `-no-pdf` | 0-byte file | complete XDV |

Raw checks:

```text
profile-worker-file-live-pdf-check\summary.json
profile-worker-file-live-xdv-check\summary.json
```

Takeaway: the worker proves that the cold-start bottleneck can be avoided, and
that the hot typesetting path is fast enough for interaction.  It is not yet a
complete interactive preview solution, because stock XeTeX finalizes PDF/XDV
only when the job exits.  To use this as a real product path, the next
breakthrough must be one of:

- make the worker handle a bounded session and exit quickly enough when the UI
  needs a committed preview;
- modify the engine/output layer to flush per-request pages or expose boxes to
  the host process;
- run a small pool of pre-warmed one-shot workers, accepting that each worker
  exits after serving one visible request.

## One-Shot Worker Pool Pressure

A one-shot worker pool was prototyped under:

```text

```

The default pool size is 5.  Each worker loads the fixed preamble, waits for one
request, writes one PDF when the job exits, and is then replaced by a new
prewarmed worker.

## Single Worker Live PDF Prototype

The single-worker path was revisited by adding a local XeTeX switch:

```text
--flush-output-on-shipout
```

The switch is implemented in the locally built XeTeX source.  It reuses the
useful part of the old Web2C IPC code path: after each `\shipout`, pending XDV
bytes are written and flushed to the output file.  It does not enable the old
TeXView socket protocol.

Changed files:

```text
ptx\texk\web2c\lib\texmfmp.c
ptx\texk\web2c\xetex0.c
ptx\texk\web2c\texmfmp-help.h
```

The updated DLL was rebuilt and copied into:

```text
mini-rebuild-test\bin\windows\xetex.dll
```

With:

```text
-no-pdf -flush-output-on-shipout
```

the live XDV file now grows after each worker request while the XeTeX process
is still running:

| Event | XDV size |
| --- | ---: |
| after request 1 | 392 bytes |
| after request 2 | 1080 bytes |
| after request 3 | 1965 bytes |
| after request 4 | 2522 bytes |
| after request 5 | 2722 bytes |
| after worker exit | 3386 bytes |

Raw data:

```text
profile-worker-flush-xdv-live-check\summary.json
profile-worker-flush-xdv-live-snapshot\snapshot-summary.json
```

`xdvipdfmx` cannot consume the live partial XDV directly because it lacks a
postamble.  A temporary postamble can be synthesized.  The postamble must
include font definitions; a minimal no-font postamble fails with:

```text
Tried to select a font that hasn't been defined
```

Using font definitions extracted from a warmup XDV, partial snapshots can be
finalized and converted successfully.
